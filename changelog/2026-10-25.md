## 权限姿态：不新建白名单机制，改用既有 sessionPolicies

- 结论：ACP 这条路**不再另建工具白名单**。DSH 插件已有按 (工作目录, ACP Agent) 精确声明权限姿态的机制 `sessionPolicies`（`packages/dsh-plugin/src/adapter.ts`），字段 `permissionMode`（approve-reads / approve-all / deny-all）与 `initialModeId`（Agent 原生模式）。插件在 `session/new` 之后立刻用 `session/set_mode` 落位，因此姿态在建会话时就生效，不会出现"第一条工具调用先卡审批"的情况。
- 根因补充：Grok Build 的原生权限模式优先于桥接层三态，`approve-all` 对 grok 不生效；grok 默认原生模式 `acceptEdits` 会直接放行 edit/move/delete，却把 execute 变成询问，于是首次 shell 调用必然进入 5 分钟等待并被自动拒绝，任务以"没有结果"结束。
- 生效点：DSH web profile 的 `oneagents-acp` 加载项新增 `sessionPolicies`，按 `cwd=/Users/scott/Documents/01-开发项目/1agents/services/dreammate-node`、`agent=grok-build` 声明 `permissionMode: approve-all` + `initialModeId: bypassPermissions`（全部放行）。需要克制时改 `initialModeId: plan`（读放行、写拒绝）或 `dontAsk`（全部拒绝）。该 profile 的用户层已同步到 `dsh-profile-web` 仓库的 `develop` 分支。
- 实测：ACP 服务在 `session/new` 的响应里即返回 `modes.availableModes`（含 `bypassPermissions`），插件的"模式必须被 Agent 公布"校验可以通过；`session/set_mode` 切到 `bypassPermissions` 后 Agent 回发 `current_mode_update: bypassPermissions`。
- 已知边界（过渡期不处理）：
  - 网关侧按 target/role 声明姿态需要 DSH 桥透传新字段并由插件消费，属于双端改造；当前生效点是"按 (cwd, agent) 声明"，与 target/role 语义等价，先用配置解决。
  - 项目级 `.1agents/allow-rules.json` 仍是"工具名 + 命令前两个空白词"的粗粒度（`Bash find .` 会连 `find . -delete` 一起放行），需要精确到命令时再扩展。
  - 审批等待仍是 5 分钟超时自动拒绝；未声明姿态的 (cwd, agent) 仍会空等这 5 分钟。
