## 1. 目标与实施顺序

先完成已有 PPT 人工审核链路，再增加报告交付。用两个实际领域检验共用边界，再据此考虑视频等场景。沿用现有 A2A、执行目标目录、任务账本、通知和工作台，不重新设计通信协议。

需要区分两种扩展：

| 扩展 | 做法 | 需要增加的内容 |
| --- | --- | --- |
| 增加一个专业角色 | 直接复用 `resident_agent` 登记 | 固定职责、技能及工具、执行预设、工作目录、输入输出约定与角色验收；无需新增交付编排 |
| 增加一个多阶段交付服务 | 登记交付目标，由领域模块协调已登记角色 | 领域输入合同、阶段推进、校验、有限返工、版本发布及进度投影 |

固定角色稳定的是职能和接单配置。每个新任务默认独立会话，同一任务的显式修订继续原上下文；多个角色可以共用执行宿主，不要求每个角色单独建立进程或端口。`skillRefs` 只是依赖说明，验收时还要确认执行宿主实际具备相应技能和工具。

第一条新增领域建议为“报告交付”：报告作者 → 独立审稿 → 人工确认 → Markdown 交付。它需要验证普通文稿审核，不依赖 PPT 页码、PNG 或 PPTX 结构。

## 2. 先收口 PPT 人工审核

源码已实现工作台与人工审核并完成隔离验证，但仍需消除已知约束冲突并做完整链路验收，然后安排部署。不能用已有六页测试证明动态页数的人审路径已经通过。

### 2.1 已知待修项

[human-review.ts](../packages/service/src/execution/human-review.ts) 的 `humanReviewPreviewSchema.slides` 仍使用 `.length(6)`；[ppt-delivery.ts](../packages/service/src/execution/ppt-delivery.ts) 已接受可选 `slideCount`，未指定时允许作者选择正整数页数。该冲突可能使非六页脚本在创建人工审核预览时失败。

下一阶段应将人工预览校验与 PPT 输入合同对齐：不指定页数时接受有效动态页数；指定时继续核验准确页数。预览和批准必须绑定同一份脚本字节，不能仅通过放宽预览数组长度绕过内容合同。本次仅记录问题，不修改代码。

### 2.2 收口验证路径

项目分析及脚本生成 → 自动校验 → 工作台待人工确认 → 用户评论 → 要求修改 → 原作者修订 → 新版待确认 → 批准新版 → PPT 制作 → 机器校验 → 独立验收 → 最终交付通知。

逐项确认：

- 未指定页数及显式指定非六页的任务都能进入人审；保留原六页场景回归。
- 评论只增加记录；要求修改把意见送回原作者会话，保留旧稿与旧轮次。
- 批准绑定父执行轮次、脚本版本和摘要；下游合同、制作和最终回执可追溯到该版本。
- 拒绝旧版放行、新字节沿用旧摘要、跨任务或不匹配执行轮次的决定。
- 重复决定、后台重复恢复和重启均不重复派发制作任务。
- 人工等待不消耗模型执行时长；取消后关闭该任务及祖先取消边界覆盖的后续派单。

完成后才能将人工审核与工作台从“源码及隔离验证”更新为相应环境的“部署验证”。记录实际包版本、部署组件和证据，不把前端构建成功等同于生产链路可用。

## 3. 保留现有基础设施，只增加三处接点

以下接口名称和字段形态均为拟议，需要结合第二领域实现确定，不代表当前公开 API。

| 接点 | 当前耦合 | 拟议调整 | 边界与兼容要求 |
| --- | --- | --- | --- |
| 目标与网关路由 | 目标绑定的 `driver` 仅允许 `ppt_delivery`，网关直接进入 PPT 分支 | 拟议 `DeliveryDriver` 接点：按目标冻结的交付模块与策略受理、恢复、取消及读取结果 | 保留已有 `ppt_delivery` 名称、配置和持久状态读取；普通 `resident_agent` 继续走现有 A2A 派单 |
| 版本化人工审核 | 审核状态模型绑定 PPT 的 `summary` 阶段及 slides 预览 | 拟议 `ReviewPayload`：保留通用身份、决定、版本与摘要绑定，领域提供带类型和版本的预览及校验 | PPT 与 Markdown 分别定义预览，决定不能任意提交下游输入；旧审核记录仍可查看与续跑 |
| 工作台进展展示 | 阶段及产物投影依赖 `PptDeliveryRun` | 拟议 `DeliveryProgressProjection`：领域提供阶段、已发生的进展、产物版本和关联任务引用 | 只读展示持久事实，不推进流程、不发通知；没有真实任务的计划阶段不伪造子任务 |

交付模块自身拥有阶段机、版本选择、返工策略和持久恢复检查点。账本仍记录执行事实，工作台仍读取投影；两者不根据阶段名称猜测下一步。拟议接口首先只服务 PPT 与报告两个实现，不提前设计任意图形工作流。

目标解析继续冻结目标配置版本、连接版本、角色绑定和交付策略。修改目标配置不得改变已受理任务；调用者可以收紧预算，不能绕过固定目录、预设或允许的协作目标。

## 4. 第二领域：报告交付试点

以下均为待实现计划。第一版优先验证纯文稿交付，不增加 DOCX、PDF、配图或发布渠道。

| 阶段 | 负责方 | 输入与交付要求 |
| --- | --- | --- |
| 写作 | 已登记报告作者 | 根据主题、受众、结构和允许使用的资料形成独立版本 Markdown；保留事实来源和限制 |
| 独立审稿 | 与作者分离的已登记角色 | 对冻结的相同文稿版本核对事实、论证、结构与需求覆盖；输出通过或具体修改意见 |
| 人工确认 | 工作台指定审核人 | 查看完整稿件、版本及审稿意见；评论、要求修改、批准或放弃分别留痕 |
| 发布交付 | 报告交付模块 | 固定获批 Markdown 的最终字节、摘要和产物引用，形成最终回执并通知原主会话 |

机器校验检查 Markdown 文件可读性、必要章节、来源引用、版本目录和字节摘要；内容正确性由独立审稿及人工确认承担，不能将文件存在视为稿件通过。

独立审稿退回时，在冻结的预算内继续原作者任务形成新版本，再审稿。人工要求修改也回原作者，形成新版本后重新独立审稿和人工确认；旧批准不自动沿用。首版应明确质量返工与人工修订的计数及上限，不通过持续重建任务绕过预算。

交付目标仅允许调用预登记作者和审稿角色。它们通过统一入口调用时创建真实子任务；本地确定性校验、预览和发布只记录内部步骤与证据，不伪造为 Agent 子任务。

## 5. 父任务、执行轮次及通知的状态边界

| 对象 | 应记录的事实 | 不能推导为 |
| --- | --- | --- |
| 父 Job | 整份 PPT 或报告的交付目标、当前状态、最终结果、子任务关联 | 单个子任务已回复就代表整个交付完成 |
| 子 Job | 作者、制作或审稿等被委派工作；保留真实执行身份和来源 | 领域内部每一步都自动创建一个子 Job |
| Attempt | 同一任务的一次执行或显式继续；返工产生新轮次并保留历史 | 覆盖旧轮次，或以新任务掩盖原任务失败 |
| 产物版本与审核 | 指定轮次和相同最终字节对应的版本、摘要及决定 | 对 A 版的通过可以放行 B 版 |
| 通知及 ack | 已生成、投递、主会话处理和确认的独立记录 | ack 等同于业务接受，或通知未确认等同于执行失败 |

等待子任务时，父交付仍在执行，并通过阶段表达等待；确需人工决定才进入 `input_required / awaiting_human`。父交付完成的前提是必需步骤、版本校验及最终结果和通知意图已持久化；不等待通知送达、ack 或最终成品的人工业务接受。脚本或文稿的中间批准与最终成品业务接受分别记录。

重启后先核对持久请求、实际后端引用、子任务状态和已记录决定，再继续推进。未知受理不得盲目重发；无法确认时显示诊断并保留证据。

主会话继续遵守“提交并落盘 → 结束本轮 → 真实通知到达 → 检查回执并记录结论 → ack”的调用边界。后台协调服务查询子任务不变成主会话轮询；开发验证与正式派单分别记录成本。

## 6. 分期实施与依赖

| 期次 | 工作及产出 | 前置依赖 | 阶段出口 |
| --- | --- | --- | --- |
| P0：PPT 收口 | 修复动态页数与人审冲突，完成修订批准、制作验收及恢复验证；保存部署方案与证据 | 当前源码快照和隔离验证记录 | PPT 原链路及非六页人工审核通过；生产状态按实际部署更新 |
| P1：角色登记与最小接点 | 登记报告作者及独立审稿人；补齐三处接点，PPT 作为兼容实现 | P0 的合同及状态语义稳定 | 普通角色可独立派单，PPT 经新接点行为一致，旧记录可读 |
| P2：报告交付 | 实现报告输入合同、有限返工、文稿预览及人审、Markdown 最终交付 | P1 的角色可用性、驱动路由与审核投影 | 报告完整路径通过，证明没有 PPT 文件结构仍可复用基础设施 |
| P3：并行与发布验收 | PPT/报告并行、多角色隔离、重启及幂等故障验证，整理配置与调用说明 | P2 完整交付 | 两领域在同一工作台运行，满足下表全部关键验收后安排发布 |

这一轮不增加通用 DAG 引擎、可视化编排器、通用插件市场或 Activepieces 强依赖。Activepieces 的执行后端与台账投影仍是可选集成；既有 `workflow` 目标不能因增加交付模块就宣称具备实际工作流执行能力。

## 7. 整轮验收清单

| 场景 | 可检查的通过标准 |
| --- | --- |
| PPT 动态页数 | 未指定页数、指定非六页、既有六页均通过脚本、人审预览、制作合同及产物数量的一致性校验 |
| 多角色并存 | 作者、PPT 制作、报告作者与独立审稿可登记并接单；固定绑定不可被单次输入覆盖，新任务会话隔离 |
| 两领域并行 | PPT 与报告任务共用执行目标目录、账本和工作台，分别显示真实阶段；分别使用自己的领域配置和发布目录 |
| 版本绑定 | 退回意见到达正确作者，新版重新审查；批准、独立审稿和发布引用相同目标版本，字节漂移及旧批准被拒绝 |
| 幂等 | 重复人工决定、重复后台唤醒、重复通知均只产生一次有效推进和交付；相同请求号不同内容明确冲突 |
| 重启恢复 | 等待子任务、等待人工、决定落盘未续跑、派发结果未知等边界可恢复或明确诊断，不盲目重派 |
| 预算与取消 | 人工等待与执行预算分开；返工有界；取消后无新的有效派单，旧产物和历史保留 |
| 历史兼容 | 老 `ppt_delivery` 配置、冻结策略、Job/Attempt、人审记录及结果可读取；不向老任务补插新审核关口 |
| 通知驱动 | 主会话派单后结束本轮；由真实通知恢复，记录结论后 ack；完成、业务接受及 ack 分开报告 |
| 可选依赖 | 不配置 Activepieces 仍可运行 PPT 和报告交付；可选台账同步故障不触发重复执行 |

每个阶段只补充覆盖真实状态风险的测试和端到端证据。隔离适配器可以验证调度及展示，但专业制作、真实角色身份与最终产物质量仍须在实际执行宿主上验证，并明确记录验证范围。
